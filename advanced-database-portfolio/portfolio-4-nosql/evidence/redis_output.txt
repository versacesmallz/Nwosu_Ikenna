       1

       0  <- expired automatically, no cleanup job needed

==========================================================================================
2. SHOPPING CART - HASH per customer, atomic field increments
==========================================================================================
redis> HINCRBY cart:20211 5001 1 ; HINCRBY cart:20211 17 2 ; HINCRBY cart:20211 17 1
       
redis> HGETALL cart:20211
       {'5001': '1', '17': '3'}
redis> HDEL cart:20211 5001  (customer removes item)
       {'17': '3'}
Why Redis: carts are written on every click, read by one user, keyed by customer, and are disposable. Keeping them out of PostgreSQL removes the highest-frequency writes from the OLTP database.

3. PRODUCT PAGE CACHE - cache-aside pattern, latency vs PostgreSQL
==========================================================================================
first request  -> cache MISS: loaded from PostgreSQL and stored with TTL 600 s
second request -> cache HIT: {'product_id': 1, 'sku': 'KSW-000001', 'product_name': 'Hair Treatment Kit 1', 'unit_price': 59597.67, 'category_name': 'Hair Care', 'business_name': 'Crown Enterprises 351', 'qty_on_hand': 468, 'avg_rating': 3.55, 'reviews': 788}

2000 product-page reads (same products, warm caches on both sides):
  PostgreSQL 5-table join : median 0.620 ms, p95 1.023 ms
  Redis GET (cache hit)   : median 0.204 ms, p95 0.345 ms
  => 3.0x faster per read; PostgreSQL is then only hit on a miss.
Invalidation rule: when a seller changes price/stock the application runs DEL cache:product:{id}; the TTL bounds staleness to 10 minutes even if an invalidation is missed.

==========================================================================================
4. FLASH-SALE STOCK COUNTER - atomic Lua script (check + decrement in one step)
==========================================================================================
redis> SET stock:5001 20
       OK
60 concurrent buyers, 20 units: sold=20, rejected=40, stock left=0  (220.3 ms)
Redis executes each Lua script atomically (single-threaded command execution), so check-and-decrement cannot interleave - the same guarantee Portfolio 3 obtained with a conditional UPDATE, but without touching the database. PostgreSQL remains the system of record: successful reservations are written to orders asynchronously and a failed payment returns the unit with INCRBY.
